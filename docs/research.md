# 調査報告：CHIMMY育成ゲーム兼時計

調査日：2026-10-31。設計への反映先：[暫定技術設計書](design.md)。

## 1. 結論

**本ボードを用い、PCで制作した2D素材を再生する構成は、有力な実装候補である。**
ただし、480×480の全画面透過アニメ、SD読み込み、音声の同時性能は今回測定していない。
「滑らかな輪郭」と「高フレームレート」は別の要件として検証する。

推奨する順序は、ボードの基礎確認、背景＋透過キャラクター＋短い音の同時再生試験、時刻・セーブの検証、ゲーム内容の拡充である。
大量の衣装や動画素材を先に制作すると、性能や形式変更による作り直しが大きい。

特に重要な発見：

1. 公式Arduino説明ページと公式GitHubのバージョン記述が一致していない。一式の出所とコミットを固定する必要がある。
2. 公式同梱LVGLは8.4.0。LVGL 9の画像形式・APIをそのまま混ぜない。
3. RTCはPMICのRTC用電源に接続される。RTC搭載だけでは、全電源を外したときの時刻保持を保証しない。
4. 256×256のRGB565＋8bit透明度でも、衣装3×動作8×30コマで約135MiB。Flashだけに全素材を入れる設計は不適切。
5. 現行電源スケッチは有用な参考だが、そのまま育成アプリのメインループにはしない。

## 3. 今回確定・更新された要件

- 主人公はBT21のCHIMMY。ユーザーから、BTSのJIMINが制作に関わった、無邪気で情熱的な努力家の子犬と説明された。
- [BT21公式紹介](https://www.bt21.com/about)でLINE FRIENDSとBTSの共同プロジェクトであること、[公式キャラクター紹介](https://www.bt21.com/character)でCHIMMYの努力家としての特徴と黄色いフードを確認した。これらのページではJIMINとの対応や子犬という記述は今回確認していない。
- メイン端末は購入済みで、USBでPCに接続されている。
- 電池、スピーカー、microSDを所有している。容量・型番・接続状態は未確認。
- ユーザー申告では画面・タッチ・音がある。今回それぞれを動作試験したわけではない。
- BABYの姿を維持する。死亡・病気を入れず、親密度と反応の解放で成長を表現する。
- 電源OFF中の経過時間を反映する。ただし長期放置による影響には上限を設ける。
- USB卓上利用では「常時表示」と「無操作消灯」を設定で選べるようにする。
- 端末UIは繁体字中国語。設計資料は今回の依頼に合わせて日本語。
- バス、交通API、バス通知、そのための通信や画面は対象外。

ケースの有無、電池仕様、SD容量・形式、長期放置の上限時間、夜間設定、OTAは未確定。

## 4. PC接続と現行ファームウェア

### 4.1 読み取り専用の確認

PC上で以下を観測した：

- `/dev/cu.usbmodem2301` と `/dev/tty.usbmodem2301` が存在する。
- USB機器名 `USB JTAG/serial debug unit` が列挙される。
- 添付スクリーンショットにはArduino IDE 2.3.10、ESP32S3 Dev Module、同じポート、`screen OFF` のログが見える。

これだけで製品名・基板リビジョン・Flash容量・現在のバイナリを認証したことにはならない。
シリアルポートは開いていない。DTR/RTS操作、リセット、書き込み、Flash読み出し、電源操作は行っていない。

リポジトリは当初READMEのみで、要件・ファームウェアは含まれていなかった。
既存の未追跡エディター設定は変更していない。

### 4.2 提供された電源スケッチ

ユーザー指定の `AMOLED_PowerSwitch.ino` を読み取り確認した。リポジトリ外の原本は編集・コピーしていない。

| コードで確認した内容                                     | 設計への反映                                                 |
| -------------------------------------------------------- | ------------------------------------------------------------ |
| CO5300をArduino_GFXで初期化し、AXP2101をXPowersLibで制御 | 表示とPMICの接続を調べる参考にする                           |
| 30秒無操作で画面消灯                                     | 新要件ではUSB用・電池用の設定へ分離する                      |
| 電池駆動で消灯後10分経過するとshutdown                   | 時計用途と競合するため、継承を自動決定しない                 |
| 電池残量5%以下でshutdown                                 | 残量の有効性・誤差・低電圧条件と合わせて再設計する           |
| PWR短押しで表示ON/OFF、長押しIRQでshutdown               | 押下時間・短長イベントの関係は実機検証する                   |
| 4.1V、300mA充電、TS測定無効化を設定                      | 所有電池の仕様に適合するか未確認。無条件に継承しない         |
| shutdown前に1.2秒表示待ち                                | 低電池時に必要な保存時間を奪うため、保存を先に行う設計にする |
| PMIC初期化失敗でも呼び出し元が処理継続                   | 新設計では電源管理の異常を明示し、利用不可機能を制限する     |
| タッチ・SD・音声・RTC・セーブ処理はない                  | このファイルだけでは各機能の動作確認にならない               |
| シリアルの改行待ち、ループ内の待機がある                 | UI応答を保証する非ブロッキング構成へ置き換える               |

スケッチ中の「RTC以外の電力ゼロ」「完全遮断」はコメント上の説明であり、測定結果ではない。
特にUSB給電中のPMIC shutdown、RTCの保持、基板全体の待機電流は別々に調べる。
充電設定・長押し設定のコメントとICの実動作が一致するかも確認が必要。

## 5. ハードウェア調査

### 5.1 メーカー資料で確認できた仕様

出典：[S1]、[S2]、[S3]、[S6]。手元基板のリビジョン一致は未確認。

| 項目    | 資料上の構成                             | 設計上の注意                                       |
| ------- | ---------------------------------------- | -------------------------------------------------- |
| MCU     | ESP32-S3R8、最大240MHz、デュアルコア     | PC向け動画・3D・生成AIの実行環境ではない           |
| メモリ  | 8MB PSRAM、16MB NOR Flash                | PSRAMは揮発性。内部RAM・DMA領域と分けて予算化      |
| 画面    | 2.16インチ、480×480 AMOLED、CO5300、QSPI | LCDのバックライトPWM前提を持ち込まない             |
| タッチ  | CST9220、I2C、割り込み・リセット線       | 座標の回転・鏡映と画面方向を合わせる               |
| PMIC    | AXP2101                                  | 給電、充電、残量取得、電源状態を一元管理           |
| RTC     | PCF85063ATL、32.768kHz水晶               | 外付けRTCとESP32内部RTCタイマーを区別              |
| IMU     | QMI8658系                                | 型番末尾・基板差分は未確認。初版の必須入力にしない |
| 音声    | ES8311、アンプ、ES7210、マイク回路       | 初版は再生のみ。録音・音声認識は対象外             |
| microSD | TFスロット、CMD/CLK/D0/D3への配線        | 採用APIと動作モードを明示する                      |
| 通信    | 2.4GHz Wi-Fi、Bluetooth LE               | 初版は必要時の時刻同期だけを想定                   |
| 電池    | 単セルリチウム電池用接続・充電回路       | コネクターの形だけで極性・適合性を判断しない       |

公式Web表の「6/9-axis」という表記から9軸を保証しない。今回必要なのは画面・タッチ・音・SD・電源・時刻である。

### 5.2 主要配線

| 用途     | GPIO                                                     |
| -------- | -------------------------------------------------------- |
| QSPI画面 | D0=4、D1=5、D2=6、D3=7、CLK=38、CS=12、RESET=39          |
| 共通I2C  | SDA=15、SCL=14                                           |
| タッチ   | INT=11、RESET=40                                         |
| RTC      | INT=13                                                   |
| SD       | CMD/MOSI=1、CLK=2、D0/MISO=3、D3/CS=41                   |
| 音声     | MCLK=42、BCLK=9、LRCK=45、出力=8、入力=10、アンプ制御=46 |
| ボタン   | ユーザーキー=18、BOOT=0。PWRはPMIC系                     |
| USB      | D-=19、D+=20                                             |

共通I2Cを各ライブラリが別設定で再初期化しないこと。排他と初期化責任を共有する。
USB・BOOT・画面・音声に使われる端子を「空きGPIO」として割り当てない。
外付けダイヤル用の安全な空き端子は、引き出し位置も含め未確定。

### 5.3 SDの重要な区別

公式Web表にはSD SPIの表記と、BSPのCMD/CLK/D0の説明が併記される。
回路図ではD3/CSも配線されており、SPI方式の配線を確認できる。
一方、CMD/CLK/D0を用いる1bit SDMMCも検討対象で、**4bit SDMMCが配線されているとは扱わない**。

Arduino側はまず明示したピンでSPI＋`SD.h`、FAT32の既知カードを検証候補とする。
性能不足なら1bit `SD_MMC` を別試験する。同時に両ドライバーから同じカードへアクセスしない。
公式の7本の直接Arduinoサンプル一覧には専用SDテストがなく、同梱GFXライブラリの一般例はボード検証の代用にならない。
SDホストと画面QSPIのSPIホスト割り当て・DMA資源の衝突も確認する。

exFATや任意容量のカード対応は未確認。マウント失敗時に自動フォーマットしない。

### 5.4 RTCの電源経路

公式回路図PDFの1ページ目を、テキスト抽出と図の表示で確認した。

- PCF85063ATLのVDDは`VCC-RTC`へ接続される。
- AXP2101の`RTCLDO`も`VCC-RTC`につながる。
- `VBACKUP`、`VBAT2`、コンデンサーの記載があるが、独立した保持用電池が実装されていることは今回確認できない。

したがって次の3ケースを分けて試験する：

1. USBを外し、主電池を接続したまま動作を続ける。
2. 主電池を接続したままPMICで本体をOFFにする。
3. USBと主電池を両方外す。

各ケースでRTCの時刻、停止・電圧低下を示すフラグ、復帰後のずれを確認する。
ケース3で長時間保持できるとは設計しない。時刻が失われてもゲームは復旧できる必要がある。

### 5.5 電池・長時間運用

電池の公称容量、許容充電電流、終止電圧、保護回路、極性、温度条件はラベル・メーカー仕様で確認する。
300mA充電や温度測定無効化を、電池の仕様確認前に標準設定としない。
燃料計の%は推定値であり、不明を0%や100%と表示しない。
バッテリー駆動時間・基板待機電流・充電中の発熱は未測定。

ボード設定、コミット、ライブラリの出所、設定ファイル、ビルドログをセットで記録する。
`^2.0.1` は厳密な固定ではないため、ESP-IDF移行時は解決済み依存関係も記録する。

現行スケッチのコメントはGFX 1.6.4、XPowersLib 0.2.6を示す。
実際にIDEが選んでいるライブラリやArduinoコアの版は未確認。
今回PATH上では`arduino-cli`は見つからなかったが、Arduino IDEがないことを意味しない。
macOS、Node.js、FFmpeg、Swiftは確認できた。Blender・GPU構成・AI制作予算は未確認。
インストールやアップデートは行っていない。

**提案：** Arduino IDE 2＋C++から開始し、公式の一式を別の検証環境で再現する。
PlatformIOへの移行は、選んだArduinoコア・ボード・音声ドライバーの対応を確認してから行う。
LVGL 9移行とゲーム機能追加を同時に行わない。

**結論：既存ペットプロジェクトの丸ごと移植より、公式ボード例を土台に、必要な状態管理だけを自作する方が今回の要件に合う。**
既存の画面設定をCheap Yellow Displayから流用しない。

## 8. 素材制作の比較

| 方法                        | 長所                                           | リスク・負担                                 | 現時点の位置付け                         |
| --------------------------- | ---------------------------------------------- | -------------------------------------------- | ---------------------------------------- |
| 基準2D絵＋部分編集          | 顔・色を合わせやすく、まばたき等が軽量         | 手足の大きな動きは手作業が増える             | 最初の少数クリップに向く                 |
| Image-to-Video              | 短い動きの案出しが速い                         | 顔・服・輪郭の揺れ、背景除去、ループ補修     | 原案生成の比較候補。完成素材とは扱わない |
| 3D＋Blender事前レンダリング | 同じモデル・カメラ・リグから衣装と動作を再利用 | モデルの権利、リグ、表情、衣装制作の初期費用 | 多数衣装を作る場合の有力候補             |
| LoRA・追加学習              | 制作パイプラインを調整できる可能性             | データ権利、GPU、検証費用、動画一貫性        | 初版の前提にしない                       |

Blenderの透過Filmによる背景分離は公式文書[S15]で確認した。
端末は完成した2D画像・音を再生し、3Dモデルや生成AIは実行しない。

提示された[Sketchfab候補][S14]はページ取得でモデルの詳細情報を確認できなかった。
作者、ポリゴン数、ダウンロード可否、ライセンス、リグは**未検証の候補情報**のままにする。
許諾の確認前に素材をダウンロード・変換・複製していない。

Runway、Firefly等は候補名としてのみ扱う。料金、出力品質、透過対応、利用条件を今回確認したとはしない。
外部AIへの素材アップロードも行っていない。
まず利用権を確認した素材または独自の仮キャラクターで性能試験し、コードと素材は分離する。
